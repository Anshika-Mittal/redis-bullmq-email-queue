# Redis Email Queue with BullMQ

A background job processing system built with **Node.js, Express.js, Redis, and BullMQ**. This project demonstrates how to enqueue email jobs, process them asynchronously using a dedicated worker, and automatically retry failed jobs with exponential backoff.

## Tech Stack

- **Node.js** — JavaScript runtime
- **Express.js** — REST API framework
- **Redis** — Stores queue data and job state
- **BullMQ** — Background job queue management
- **ioredis** — Redis client used internally by BullMQ

## Features

- Add welcome-email jobs through a REST API.
- Process jobs using a separate worker.
- Keep API requests separate from background processing.
- Configure up to 3 job attempts.
- Use exponential backoff between retries.
- Track job completion and failure through worker events.
- Simulate email processing with a delay.

## How It Works

1. The client sends a request to `POST /welcome-email`.
2. The API adds a `send-welcome-email` job to the BullMQ queue named `emails`.
3. Redis stores the queue and job state.
4. A separate worker listens to the `emails` queue and picks up available jobs.
5. The worker simulates email processing and logs the job details.
6. BullMQ marks successful jobs as completed.
7. If processing fails, BullMQ retries the job according to the configured retry policy.

## Architecture

## Getting Started

### 1. Prerequisites

Install the following:

- [Node.js](https://nodejs.org/)
- [Bun](https://bun.sh/) or npm
- [Redis](https://redis.io/)

Redis must be running locally or accessible through the configured connection.

### 2. Clone the Repository

```bash
git clone https://github.com/Anshika-Mittal/redis-bullmq-email-queue.git
cd redis-bullmq-email-queue
```


### 3. Install Dependencies

Using Bun:

```bash
bun install
```

Or using npm:

```bash
npm install
```

Ensure that your project dependencies include:

```bash
npm install express bullmq ioredis
```

### 4. Configure Redis

The queue connects to Redis at:

```text
localhost:6379
```

The API currently uses `REDIS_URL` if the environment variable is set, otherwise it defaults to `redis://localhost:6379`.


### 5. Start the API Server

Run the API using your configured script, or execute it directly:

```bash
node api.js
```

The API listens on:

`http://localhost:3000`

### 6. Start the Background Worker

Open a **second terminal** in the same project directory and run:

```bash
node worker.js
```

The worker must be running separately from the API so it can consume and process jobs.


## API Documentation

Base URL: `http://localhost:3000`

### Add a Welcome Email Job

**Endpoint:** `POST /welcome-email`

**Content-Type:** `application/json`

Request body:

```json
{
  "to": "user@example.com",
  "name": "Anshika"
}
```

**Example response:**

```json
{
  "message": "Email added",
  "jobId": "1"
}
```

The job ID shown is illustrative. The actual ID is generated by BullMQ unless explicitly configured.

If `name` is omitted, the application uses `"Reciever"` as the default name.

### Job Details

The API creates a job with the name `send-welcome-email` and a data object containing:

```json
{
  "to": "user@example.com",
  "name": "Anshika"
}
```

The queue configuration specifies:

- **Attempts:** 3 total attempts, including the initial attempt.
- **Backoff type:** Exponential.
- **Initial delay:** 1000 milliseconds.

With exponential backoff, retry delays grow after successive failures. Under BullMQ's standard exponential strategy, the approximate delays are 1 second and 2 seconds before the second and third attempts, respectively, excluding processing time and scheduling overhead.

## Worker Processing

The worker listens to the `emails` queue and processes each job.

For every job, it:

1. Logs that processing has started.
2. Waits approximately 1.5 seconds to simulate work.
3. Logs the job ID, job name, and job data.
4. Emits a completion event when the job succeeds.

Example output:

```text
Processing..
Completed:  1 send-welcome-email {
  to: 'user@example.com',
  name: 'Anshika'
}
Completed 1 send-welcome-email {
  to: 'user@example.com',
  name: 'Anshika'
}
```

The completion information may appear twice because the worker logs the job inside its processor and also has a `completed` event listener.

**Note:** This project simulates email processing. It does not send real emails or integrate with an email provider.

## Retry Mechanism and Exponential Backoff

BullMQ allows failed jobs to be retried automatically.

The job configuration is:

```javascript
{
  attempts: 3,
  backoff: {
    type: "exponential",
    delay: 1000
  }
}
```

If a job fails, BullMQ can retry it according to this configuration, up to the configured maximum number of attempts.

Exponential backoff avoids retrying immediately and repeatedly, giving temporary failures time to recover.

The current worker simulates a delay but does not deliberately throw an error. To test retries, introduce a controlled failure in the processor during development.

## Redis and BullMQ Concepts Learned

- **Producer:** The Express API creates and enqueues jobs.
- **Queue:** BullMQ manages pending jobs and their states.
- **Consumer/Worker:** A separate process handles jobs asynchronously.
- **Redis:** Stores queue-related data and supports coordination between producers and workers.
- **Retries:** Automatically rerun jobs that fail.
- **Exponential backoff:** Increase the delay between retry attempts.
- **Job lifecycle:** Understand waiting, active, completed, and failed states.
- **Event listeners:** React to job completion and failure.
- **Separation of concerns:** Keep request handling independent from longer-running tasks.
